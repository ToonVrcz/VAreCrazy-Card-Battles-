# แผนเชื่อม Dynamic Avatar กับโปรไฟล์ผู้เล่นจริง (ร่าง — รออนุมัติ)

สถานะ: **แผนเท่านั้น ยังไม่แก้ระบบใดๆ** (ไม่แตะ Authentication / ฐานข้อมูล / engine / Production)
ที่มา: คำสั่งเจ้าของ 2026-11-27 — YOU = รูปผู้เล่นที่ล็อกอิน, OPPONENT = รูปคู่แข่ง, กรอบ Fantasy Gold, ไม่มีรูป = Default Avatar, `object-fit: cover`, ไม่เปิดเผยข้อมูลส่วนตัว

## 1. สิ่งที่ตรวจพบในระบบเดิม
- ตาราง `players` (migration 013) มี: `id, key_hash, name, points, vrcoin, pvp_matches, created_at` → **ไม่มีฟิลด์รูป**
- ผู้เล่นเป็นโปรไฟล์ guest (คีย์ลับในเบราว์เซอร์ เก็บเฉพาะ hash) ยังไม่ผูกบัญชี Universe (repo Universe ยังไม่เชื่อมต่อ)
- ห้องออนไลน์ส่งชื่อผู้เล่นให้อีกฝั่งผ่าน `RoomService.names()` (ชื่ออย่างเดียว ไม่ส่ง id/คีย์) → เพิ่มรูปได้ในแนวเดียวกัน
- **CSP ของเว็บ:** `img-src 'self' data: blob:` (vercel.json) → รูปจากโดเมนภายนอกจะ **ถูกบล็อก** ต้องใช้รูปที่เสิร์ฟจากโดเมนเราเอง (`/media/*` rewrite ไป Supabase Storage อยู่แล้ว) หรือแก้ CSP อย่างระมัดระวัง
- ปัจจุบันหน้าโปรไฟล์ในเกมแก้ได้แค่ชื่อ (`PUT /api/profile`)

## 2. ทางเลือก
| | ที่มาของรูป | ต้องแก้อะไร | ความเสี่ยง | คำแนะนำ |
|---|---|---|---|---|
| **A** | **เลือกจากชุดอวาตาร์ที่ Admin อัปโหลดไว้ใน CMS** (ผู้เล่นเลือกเอง) | เพิ่มคอลัมน์ `players.avatar_id` (nullable) + endpoint เลือกอวาตาร์ + แสดงในห้อง | ต่ำ: ไม่มีรูปส่วนตัว ไม่ต้องคัดกรอง ใช้ `/media` ผ่าน CSP เดิมได้ | **แนะนำทำก่อน** |
| B | ผู้เล่นอัปโหลดรูปเอง | คอลัมน์ + อัปโหลด + ตรวจไฟล์ + คัดกรองเนื้อหา + พื้นที่เก็บไฟล์ | สูง: ภาพไม่เหมาะสม/ข้อมูลส่วนตัว/ค่าพื้นที่ | ไม่แนะนำตอนนี้ |
| C | รูปโปรไฟล์จากบัญชี Universe (ตอนเชื่อมแล้ว) | เพิ่ม `avatarUrl?` ใน `ModuleSeat` (adapter) + อนุญาตโดเมน (CSP/พร็อกซี) | กลาง: ต้องรอเชื่อม Universe และตัดสินเรื่องโดเมน | ทำภายหลังเมื่อเชื่อม Universe |

ทาง A รองรับ C ในอนาคต: ฝั่งหน้าจอรับ "URL รูป หรือ ไม่มี" แบบเดียวกัน (ที่ prototype ทำไว้แล้ว) แหล่งที่มาเปลี่ยนได้โดยไม่แก้หน้าจอ

## 3. แผนทาง A (ถ้าอนุมัติ)
**ต้องได้รับอนุญาตก่อน (แยกชัดเจน):**
1. migration ใหม่ `034_player_avatar` — เพิ่มคอลัมน์ `avatar_id` แบบ nullable (additive ย้อนกลับได้ด้วย down migration, ไม่กระทบข้อมูลเดิม ไม่แตะระบบ login)
2. endpoint ใหม่ `PUT /api/profile/avatar` (ต้องมีคีย์ผู้เล่นเหมือน rename; ตรวจว่า `avatar_id` อยู่ในรายการที่อนุญาตเท่านั้น)
3. Deploy edge function ตามขั้นตอนปกติ (รอคำสั่ง "Deploy")

**ขั้นตอน**
1. Admin: ตั้งหมวด "อวาตาร์" ในคลังสื่อ CMS (ใช้ระบบ media เดิม) + ภาพ Default Avatar (A02) + กรอบทอง (A01)
2. DB: migration 034 (+ down)
3. Server: `economy`/`api` เพิ่ม get/set avatar; `rooms.names()` → คืน `{name, avatar}` เฉพาะ **path รูป** (ห้ามส่ง id/key/อีเมล)
4. หน้าเกม `/play`: หน้าโปรไฟล์เลือกอวาตาร์ · ห้อง/สนามแสดงรูปฝั่ง YOU / OPPONENT ผ่าน component ที่ทำใน prototype (fallback เป็น Default อัตโนมัติ, `object-fit: cover`, `referrerpolicy=no-referrer`)
5. ทดสอบ (vitest + PGlite + e2e local): ไม่มีรูป → Default · เลือกรูป → แสดงทั้งสองฝั่ง · id ไม่อยู่ในรายการ → ถูกปฏิเสธ · มุมมองคู่แข่งไม่รั่วข้อมูลอื่น · บอท/ห้องเก่าไม่พัง
6. ทำบน branch แยก รอคำสั่ง "Deploy" (ลำดับ: migration → edge → merge → ตรวจ)

**ย้อนกลับ:** down migration ลบคอลัมน์ · เอาโค้ดแสดงรูปออกแล้วทุกคนกลับไปใช้ Default Avatar (หน้าเกมไม่พัง)

## 4. ข้อกำหนดความเป็นส่วนตัว/ความปลอดภัย (ใช้กับทุกทาง)
- ส่งให้อีกฝั่ง **เฉพาะ path/URL รูปและชื่อที่แสดง** ไม่ส่ง player id, key hash, อีเมล, แต้ม, การ์ดในมือ/เด็ค
- รับเฉพาะรูปที่เสิร์ฟจากโดเมนที่อนุญาต (ทาง A = `/media/...` ของเราเอง) ไม่รับ URL ที่ผู้เล่นพิมพ์เองโดยตรง (กันการติดตาม IP คู่แข่ง)
- รูปที่โหลดไม่ได้ → Default Avatar ห้ามแสดงภาพแตก
- ผู้ชมห้อง (spectator) เห็นรูปเท่ากับที่เห็นชื่อ ไม่เพิ่มข้อมูลอื่น

## 5. สิ่งที่ต้องการให้เจ้าของตัดสินใจ
1. เลือกทาง **A / B / C** (แนะนำ A แล้วต่อ C ภายหลัง)
2. ถ้า A: อนุญาตให้เพิ่ม migration `034_player_avatar` และ endpoint `PUT /api/profile/avatar` หรือไม่
3. จำนวนอวาตาร์ที่ต้องเตรียมในชุดแรก (เสนอ 8–12 แบบ ใช้ภาพจากแชทที่ออกแบบ) และ Default Avatar 1 แบบ
